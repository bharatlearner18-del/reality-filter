# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **validation-first MVP** for "Reality Filter" — a hype-vs-reality check for AI launches. A user pastes an AI launch/tool/topic and gets a verdict (`worth trying now` · `watch later` · `too early` · `mostly fog machine`) backed by an evidence packet. This is a demand test, **not** the real product — there is intentionally no backend, database, or build system yet.

The two markdown files are the product's source of truth, written as pre-PRD specs:
- `research-brief.md` — the decided model, MVP scope, validation plan, and open questions.
- `deep-research-report.md` — market/moat analysis behind the brief.

Read these before changing product behavior. Key locked decisions from them:
- **Scope is locked to AI launches only** (Option A, confirmed with the user). It is explicitly NOT a competitor tracker, strategy advisor, or daily news feed. Do not broaden the subject to "any company/tool/news."
- **Do NOT build the backend/automation yet.** Building it before real users show up is the documented trap. Concierge/manual delivery is the plan until demand + willingness-to-track are proven.
- The moat is the **public dated track record** + the **Premium tracking workflow**, not the research itself (ChatGPT/Perplexity already do ~80% of the raw research).
- **The track record is a hand-picked selection, NOT a log of everything we research** (re-confirmed with the user 2026-07-30, after an `about.html` explainer scene wrongly implied otherwise and had to be cut; **re-confirmed a third time 2026-08-01** — see the publishing rule below). Most packets never appear on `track-record.html`, and that is correct, not a backlog to clear. Adding a key to `LEDGER_ORDER` is a deliberate editorial decision **the user makes**, only when they decide that call is worth standing behind publicly — a few a month at most. Filing a packet in `PACKETS` does not earn it a ledger row, and **no page may state or imply that every check gets published.** Any copy describing the record must read as a curated selection ("the calls we choose to stand behind"), never as a complete history. See `RESEARCH-RUNBOOK.md` → "Track record stays curated, separately", and the disclosure risk: the public counts on `track-record.html` must only ever claim the curated record, never total research volume.
  - **The publishing rule, in the user's own words (2026-08-01):** *"we will only upload and stay there data on track record that we want… we will not upload every data on track record and when we will want we will just upload it, depends on me."* Three things follow. (1) **Only selected packets go on the record** — selection is the default state, not an exception. (2) **What is already on the record stays there** ("stay there") — rows are not quietly removed when a call ages badly; a wrong call gets re-checked and acknowledged, per the re-check rule under Content integrity. (3) **Timing is the user's call too** — there is no schedule, no queue to drain, and no "we should publish this now" prompting. Claude never adds a key to `LEDGER_ORDER` on its own initiative; it asks, or waits to be asked.
  - **The homepage lede is the canonical public statement of this rule.** It currently reads *"Evidence, not marketing copy. Selected calls go on a public, dated record. Free."* The load-bearing word is **"Selected"** — it is what keeps the sentence honest, and it must survive any future rewrite of that line. **Do not restate the rule as a promise about our behaviour** ("we never delete a call we got wrong", "every verdict stays up"): that was tried on 2026-08-01 and reverted the same day, because a behavioural promise is a commitment the user has to keep forever and cannot loosen later without looking like a retraction. Describing *what the record is* ("selected calls") leaves the user free to publish more, publish less, or change the policy, and no public sentence has to be walked back. Any replacement for that line must (a) keep an explicit selectivity word, and (b) describe the record rather than pledge future conduct.
- **User research requests stay manual, per the point above** (2026-07-24): when someone searches a launch that isn't filed, `renderCapture()` collects their email via Formspree (`type: 'packet request'`) — that part is already automatic. Everything after (researching it, writing the packet, publishing it, emailing the user their link) is a manual/concierge step, not a live pipeline — see **`RESEARCH-RUNBOOK.md`** for the exact process. The key mechanism: a packet added to `PACKETS` (in `packets.js`) is searchable/readable on `index.html` immediately; it only appears on the public track record if its key is also added to `LEDGER_ORDER`. Keeping a packet out of `LEDGER_ORDER` is how a user-requested verdict stays answerable without inflating the curated, few-per-month track record. Don't build an automated research/publish pipeline without the user explicitly asking for it again with full awareness of the cost/hosting/review tradeoffs (already discussed and declined once).

### Architecture (tool logic in `index.html`, data in `packets.js`)
- **`PACKETS` object (`packets.js`)** — the single source of truth for content. Each key is a filed launch with `match` (lowercase substring aliases used for lookup), `date` (for the ledger), the packet fields (`claim`, `stakes`, `found`, `missing`, `signals`, `pricing`, `next`), and the verdict (`verdict`, `verdictClass`, `fog`/`fogLabel`/`fogWhy` for the hype meter). To add or edit a packet, edit this file — both the tool and the track record pick it up. Add its key to `LEDGER_ORDER` to show it in the track record. **Every packet must follow the packet-writing standard** (see Content integrity below) — `stakes` is required, not optional; `renderPacket()` renders it as the "Why this matters" row and prints `undefined` if it's missing.
- **`findPacket(q)`** (in `index.html`) — matches loosely-phrased queries, not just exact aliases. Match → `renderPacket()` (evidence packet). No match → `renderCapture()` (email-capture panel). Two ways to hit:
  - **(a)** the query **contains** a whole alias verbatim — so `"heyy the new launch of chatgpt..."` matches a `chatgpt` alias.
  - **(b)** after stripping conversational filler (the `STOP` set — the/new/launch/tell/about/version/update/…), the query's remaining **content words equal an alias's content words as a set** — so `"gemini version 3"` matches alias `"gemini 3"` regardless of word order or filler.
  - **(b) is set-EQUALITY, not subset — that safety is the whole point.** Subset ("every alias word appears somewhere") would also match `"Gemini Ultra 3"` to a `"gemini 3"` packet, a *different product*, because a tier word looks like filler. Equality rejects it (`{gemini,ultra,3} ≠ {gemini,3}`). **`STOP` must hold only conversational filler — never product/tier words** (pro, ultra, mini, sol, turbo, numbers, or single letters that could be a token); adding one would let that word be stripped and cause a cross-tier mismatch.
  - **When filing a new packet, eyeball its aliases' content keys against existing packets'** (lowercase, strip `STOP`, dedupe, sort). If two packets share a content key, path (b) silently gives the one earlier in `PACKETS` — the same first-wins hazard as bare-word aliases. Current three don't collide.
  - **Miss rather than mismatch.** A fragment like `"ai"`, `"able"`, `"sales"`, or a bare brand word (`"gpt"`, `"claude"`) is neither contained as a whole alias nor equal to an alias's content set, so it still routes to the email capture — the demand signal we exist to collect. A wrong verdict costs trust, which is the moat; a miss we just answer by hand. When a real phrasing still misses, the fix is **adding an alias to `match`** in `packets.js` — that list is the control point. Do NOT add a bare `"gpt"`/`"claude"` alias to force bare-word matches: once a second GPT/Claude packet is filed, whichever sits earlier in `PACKETS` silently wins every such query (use a disambiguation UI then, not a broader matcher).
  - **One accepted edge:** path (a) is a plain substring, so `"gemini 3 pro"` still matches a `"gemini 3"` alias (it contains it verbatim), even though Pro may be a different tier. This is unchanged from the original substring matcher; `"Gemini Ultra 3"` is only safe because "ultra" sits mid-phrase and breaks the contiguous substring.
- **The packet renders in two zones (2026-07-25, user request: "easy to read… able to take decisions").** `renderPacket()` shows a **decision zone** — `Why this matters` → `Hype risk` → `What you should do` — and puts the five evidentiary rows (`Official claim`, `Proof found`, `Proof missing`, `Experts & real users`, `Pricing & limits`) inside a `<details class="evidence">` that is **closed by default**. Before this, a packet opened at 452 words / ~1.9 screens with the hype meter and next step rendered *last*, so the reader waded through ~336 words of evidence before reaching the actual call; it now opens at ~186 words / ~1.1 screens. The evidence is one click away and the `<summary>` names every section inside — do NOT hide it further or drop that summary line, because the evidence is the moat and it must read as present, not withheld. `next` is authored as `Audience: advice.` segments (packet-writing standard) and `nextSteps()` splits it into one card per audience so a reader finds their own row; a packet that doesn't follow the pattern degrades to a single unlabelled card. That splitter deliberately avoids regex **lookbehind** — Safari <16.4 throws on `(?<=` at parse time, which would kill the whole inline `<script>`.
- **The "Track this" CTA under the packet was removed 2026-07-23** (user decision). It used to render a `.track-cta` strip with a "Track this →" button under every verdict, but because it fired an anonymous signal and confirmed "You're on the list ✓" without ever collecting an email, it read as a hollow/confusing promise. The whole block (markup in `renderPacket()`, the `[data-track]` handler, and the `.track-cta`/`.tc-*`/`.btn-ghost` CSS) is gone. Per-launch tracking interest used to be captured via the Pricing page waitlist, which was parked 2026-07-30 — so **nothing on the site captures it at the moment**. Don't re-add a track button without an email field.
- Example chips and the `?q=` deep-link both call `showResult()`; the track-record rows (in `track-record.html`) deep-link into it via `index.html?q=<name>`.

### Forms → Formspree (`forms.js`)
The no-match email capture on `index.html` posts through `sendSignal()` in **`forms.js`**. It is the **only live form on the site**: the Premium/Pricing waitlist was parked along with its page on 2026-07-30 (archived in `PRICING-PARKED.md`), so `forms.js`'s `type:'premium waitlist'` path has no caller right now. Leave that path in place — restoring the page brings it back. (History: a "Track this" button and a standalone feedback form also used this, both removed 2026-07-23.)
- **`FORMSPREE_ID` at the top of `forms.js` is the only thing to set.** Paste the ID from `https://formspree.io/f/XXXXXXXX`.
- **While it's empty every form stays a stub**: `sendSignal()` returns `{ok:true, skipped:true}`, so the success state shows and nothing is sent. This is deliberate — the design handoff shipped a hardcoded `YOUR_FORM_ID` placeholder that made *every* submit fail with an error, and this is the guard against repeating that. An unconfigured site must never show users an error.
- Both post to the **same endpoint**; the `type` field (`packet request` / `premium waitlist`) tells them apart in the inbox, which keeps it inside Formspree's free single-form tier. `page` is added automatically.
- On a real send failure (network down, 4xx) `sendSignal` returns `{ok:false}` and the handler re-enables the form and shows `.form-err` — never a silent success, since the user believes they're on the list.

## Design system (keep consistent when editing UI)
Concept: a warm parchment-canvas editorial shell modeled on **Claude/Anthropic's** product design language (this replaced an earlier Cursor-style reskin — cream canvas, sans-only Inter, hairline-only depth, orange accent — which the user deliberately abandoned in favor of this look; do not revert to the Cursor system described in old history without being asked). The pairing is **serif headlines + sans body/UI**: `.display`, `.packet-name`, `.section h2`, `.premium .p-title`, and `.capture h3` all use the book-serif `--font-serif` at weight 400 with only slight negative tracking (serif tracks badly with tight negative letter-spacing — don't push it past about `-.01em`); everything else (body copy, nav, buttons, mono labels) stays on Inter/JetBrains Mono. Depth is **soft shadow, not hairline**: outer cards (`.packet`, `.capture`, `.ledger`) use `--shadow-card` instead of a `border`; hairlines (`--hairline`/`--hairline-strong`) are kept only for *internal* dividers (packet rows, ledger rows). Signature elements unchanged in role: the white evidence card and the hype-risk "fog meter". (The ink-inverted Premium band was the third; it's parked with `premium.html` as of 2026-07-30 — its CSS is intact and it keeps that role if the page returns. See the `premium.html` PARKED bullet above.)
- Fonts: `Source Serif 4` (`--font-serif`, headlines only), `Inter` (`--font-sans`, body/UI), `JetBrains Mono` (`--font-mono`, every label/data/caption/ledger surface). All three loaded via the Google Fonts `<link>` in both HTML pages — if you add a font weight/style, update that link, not just the CSS var.
- Surfaces: `--canvas` (#f0eee6 warm parchment page floor) → `--surface-card` (#fff white cards: packet, capture, ledger, chips, inputs) → `--surface-strong`/`--canvas-soft` (soft fills) → `--ink` (#3d3929, the one "inverted featured" surface — it was the Premium band, which is parked as of 2026-07-30, so nothing currently uses `--ink` as a *surface*; it's still the standard text colour). Outer cards float via `--shadow-card`; hairlines still separate rows *within* a card.
- **Claude terracotta (`--primary` #d97757) is the single brand voltage and stays scarce** — only the true conversion CTAs (`.btn` search/capture/waitlist), the `.real-word` hero accent, and the `.shine` glint (below). The nav is otherwise plain text links (no button), which keeps the accent rare and avoids a redundant CTA next to the search bar. Don't paint eyebrows, labels, or borders terracotta as decoration.
- **`.toplink.shine`** marks a demand-signal link we most want acted on. **No page currently uses it** — it was on the nav **Premium** and **Feedback** links and the footer feedback CTA, all since removed (Premium parked 2026-07-30). The rule is kept for whenever such a link returns. The text stays `--ink` (bold, AA-legible) while a terracotta+light glint sweeps across it via `background-clip:text` — deliberately NOT solid terracotta, because terracotta text on cream is only ~2.7:1 and fails AA at nav size. Under `prefers-reduced-motion` it falls back to solid bold `--ink`. Any hardcoded `rgba(...)` shadow/border tied to the accent (focus rings, badge borders) must use the terracotta RGB (217,119,87), not the old orange (245,78,0) — grep for `245,78,0` if you see an orange-tinted ring after a color-token change.
- Small mono labels on cream/white use `--label` (#6b6552), a tone tuned to clear ~4.5:1 at caption size; `--muted`/`--muted-soft` are for larger or secondary text only (they fail AA at 11–13px).
- **AI-timeline pastels** (`--tl-thinking/grep/read/edit/done` — peach/mint/blue/lavender/gold): scoped to the evidence packet's row dots as "investigation stages." As of 2026-07-25 these are keyed to **semantic classes, not `:nth-child`** — `.row.r-claim`/`.row.r-stakes`=peach · `.r-experts`=blue · `.r-pricing`=lavender · `.r-hype`=mint · `.r-next`=gold, with `.row.found`/`.row.miss` keeping semantic green/red. The old positional selectors broke the moment rows moved (see the packet's two-zone layout below), and they also outranked `.found`/`.miss` by specificity. **When you add a row to `renderPacket()`, give it an `r-*` class and add a rule — never a positional selector.** Row animation delays are still positional but scoped with `>` to each zone (`.packet-body>.row` 1–3, `.ev-body>.row` 1–5).
- Verdict colors are a 4-point scale via CSS vars/classes, darkened to read on white/cream: `v-go` (green), `v-watch` (gold), `v-early` (blue), `v-fog` (red/pink). Use these, not one-off colors.
- All colors/spacing come from CSS custom properties in `:root`. Derive new styles from those tokens.
- **Dark mode** is a manual toggle (not `prefers-color-scheme`): the `.theme-toggle` button in the nav flips a `dark` class on `<html>` (so the selector everywhere is `html.dark`, not a bare `.dark`), and the choice persists in `localStorage` under `rf-theme`. Every page carries a tiny inline script in `<head>` that re-applies the saved class *before paint* to avoid a flash of the light theme — if you add a page, copy that script or it will flash. Dark styling is done by overriding the same `:root` tokens under `html.dark`, so new components theme themselves for free **as long as you use the tokens** rather than hardcoding a hex. The `html.dark` block near the top of `styles.css` is the exception that proves the rule: a few gradient stops there (`#343128`, `#34322c`, `#3a3129` on `.track-cta` / `.fb-inpage`) are bespoke tints with no token equivalent. Leave them, but don't add more — if you need a dark-only color that a token already covers, use the token.
- **Premium band layout** (**currently parked** — kept because `PRICING-PARKED.md` restores the page verbatim and this is the rule that page depends on): `.premium` is a slim full-width horizontal flex band (pitch in `.p-left`, email form in `.waitlist` on the right) so it never reads as a second hero or gets confused with the search bar. Its heading is `<h2 class="p-title">` styled via `.premium .p-title` — that two-class selector deliberately outranks the generic `.section h2` rule (a known cascade collision); do NOT restyle it as a bare `.premium h2` or with `!important`.
- **Footer** is the same on all three pages: one `.fwrap` brand row (`Reality Filter` blurb left, a single `.toplink` right — "Check the track record →" on `index.html`, "← Back to check a launch" on the other two). Below it sits `.disc`, the fine print — on `index.html` it also carries the **Formspree disclosure**, because it's the only page that collects data now; `about.html`/`track-record.html` collect nothing so their `.disc` stays the short version. (History: the launch-page footer used to carry a second `.fb-row` "Give us your feedback →" row, and before that a `.fb-invite` dashed pill. Both are gone with `feedback.html`; the `.fb-*` CSS remains unused.) `.disc` sets `max-width:60ch` to override `footer p`'s 46ch, which at 11px mono is only ~304px and wrapped the disclosure into four cramped lines.
- **Mobile (≤720px) nav**: brand left, the three links (Product · How it works · Track record) plus the theme toggle right-aligned. When they don't fit beside the brand the `.topbar .wrap` flex-wraps them onto a second row under it (topbar grows to fit); the brand never wraps. Don't hide `.nav-center` — those links are the only route to the track record on phones. Other mobile rules that look odd but are load-bearing: `.btn` gets real vertical padding (it collapses to ~20px tall when it wraps off the input's flex line), and `.ledger-row .vd` allows wrapping so long verdicts ("Worth trying — with caveats") stay inside the ledger card.

## Automated review (two subagents, auto-triggered)
After any code change, TWO review subagents run automatically to check it before the user sees it:
- **`code-reviewer`** (`.claude/agents/code-reviewer.md`) — bugs and quality issues.
- **`security-reviewer`** (`.claude/agents/security-reviewer.md`) — XSS, injection, data leaks, risky third-party loads.

Both load the `find-skills` skill first, are read-only (report, don't edit), and run in parallel. Wiring is in `.claude/settings.json`: a `PostToolUse` hook flags `.claude/.review-pending` when a `.html`/`.css`/`.js` file is edited, and the `Stop` hook injects a reminder to dispatch both reviewers before the turn ends (then clears the flag). To pause, remove the `Stop` hook from `.claude/settings.json`. Note: after editing `.claude/settings.json` you may need to reload config (`/hooks` or restart) for changes to take effect.

## Content integrity
Verdicts are the product's only asset — accuracy is the whole point. Packet content must be real and evidence-based (researched from current sources), never invented placeholder data. A wrong "worth trying now" damages trust, which is the moat.

### Packet-writing standard (product behavior, not a one-off)
Set with the user 2026-07-18: a packet that only lists facts is a failed packet — the reader must feel why it matters to *them*. Every packet (new or re-checked) must:
- **Open with stakes.** The `stakes` field ("Why this matters" row) addresses the reader directly — founder, builder, buyer — and says what decision this verdict changes for them. Second person, concrete ("this decides whether you re-run your evals this month"), never generic ("this is an important development").
- **Name the evidence.** Numbers with sources in the text itself (benchmark names + scores, filings, named reviewers like Simon Willison / METR / The Verge), not vague "reports suggest." Research fresh at filing time — the WebSearch/WebFetch step is mandatory, per the rule above.
- **Separate signal from hype explicitly.** `found` = what's independently verified; `missing` = where the official claim outruns the evidence; `signals` (rendered as "Experts & real users") = what named experts, real users, and companies actually say/do — including evidence *against* our own verdict when it exists (both-sides candor is what makes the verdict credible).
- **Segment the next step by reader.** `next` gives different advice to builders vs buyers vs everyone else, not one generic recommendation. **This is now load-bearing markup, not just style:** `nextSteps()` splits `next` on the `Audience: advice.` pattern to render one card per reader. Author every `next` as `Label: advice.` segments — a label is a short noun phrase (no periods inside it), each segment ends with a period. Break the pattern and the packet silently degrades to one unlabelled card.
- **The reader must be able to decide WITHOUT opening the evidence panel** (standing rule, set with the user 2026-07-25 — "every verdict should be like this, understandable"). The packet opens showing only three fields: `stakes` → `fog`/`fogLabel`/`fogWhy` → `next`. Those three carry the entire decision on their own; `claim`, `found`, `missing`, `signals` and `pricing` are one click away and must be treated as *support*, never as the place the actual call lives. Concretely, when writing or re-checking any packet:
  - `stakes` — second person, names the decision at risk. No benchmark names, no vendor jargon.
  - `fogWhy` — one plain-language sentence on *why* the risk sits where it does. It renders beside the meter, so it must read standalone ("the capability is real — the fog is trust: an unpublished hallucination rate…").
  - `next` — concrete and testable ("run your own evals on your repo this week"), never "keep an eye on it".
  - Anything a reader needs to *act* belongs in these three. Anything that only *proves* the call belongs in the evidence rows.
  - After filing, re-read only the decision zone. If you can't tell what to do from it alone, the packet isn't finished — move the deciding sentence up, don't leave it buried in `found`.
- **Re-check, never quietly edit.** When facts change, update the packet AND its `date`, and state the change inside the packet body (e.g. `found` opens with "Updated 2026-07-18 — we filed this 'Too early' on Jul 14…"). Verdict changes are allowed and are the product working — GPT-5.6 went "Too early" → "Worth trying — with caveats" when GA arrived; the old call stays acknowledged on the record. The `.ledger-note` on track-record.html hand-carries the latest re-check date — update it too.
